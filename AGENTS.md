# Port Azure — agent guide

A SNES-era **isometric** tile RPG in Godot 4.7.2. Nobody runs the editor: every
change is a text edit, validated by headless Godot, published to GitHub Pages
as a web build. Assume you cannot open a GUI. Everything below exists so you do
not have to.

Maps are still square ASCII grids; `CLAUDE.md` explains why isometric is a
projection and not a data format. This file is about the pixels.

If you are here to work on **artwork**, read "Seeing your work" first. It is
the part that makes the difference between guessing and knowing.

If you are here to work on **lighting, maps or new assets**, read
`docs/architecture/AGENTS.md` — the checklists for a new room or prop, the
metadata schema, and the shortcuts that are forbidden. The one-line version:
lighting is driven by metadata (`"lighting"` blocks in `tiles.json` and
`maps/*.json`), never by tile names in code and never by nodes in a `.tscn`.

## Commands

```bash
tools/ci.sh setup      # download Godot + web export templates into .tools/
tools/ci.sh import     # re-import assets; run after touching assets or scenes
tools/ci.sh generate   # redraw art, rebake the tileset, re-render docs/art/
tools/ci.sh sheets     # re-render docs/art/ only — needs no Godot at all
tools/ci.sh shots      # screenshot the running game into docs/shots/ (needs xvfb)
tools/ci.sh test       # the whole suite, ~2 seconds
tools/ci.sh export     # web build into build/web/
```

`tools/ci.sh test` is the gate. It fails on assertion failures **and** on any
`SCRIPT ERROR` or `ERROR:` the engine prints, because Godot otherwise exits 0
with a fundamentally broken project. One suite only: `tools/ci.sh test -- --only maps`.

Python is standard-library only — no Pillow, no `openai` package, nothing to
install. Keep it that way; it is why the generators run in any sandbox.

## Seeing your work

You cannot judge a 32×16 diamond at 1:1, and you cannot judge a tile at all
outside the map it sits in — in an isometric world a tile's whole job is to
meet its neighbours, and a tile alone tells you nothing about whether it does.
So:

```bash
tools/ci.sh sheets
```

then **open these images and actually look at them**:

| File | Shows |
| --- | --- |
| `docs/art/atlas.png` | every tile at 5×, named, ground diamond outlined, solid tiles framed in red |
| `docs/art/actors.png` | every actor, 4 directions × 4 frames, at 4× |
| `docs/art/palette.png` | every colour in `tools/pixel.py` with its hex |
| `docs/art/map_port_azure_town.png` | the town composited from real map data at 3× |

The outlined diamond on the atlas sheet is the check that matters: art floating
above it, or spilling past it, is art that will not line up in the game.

`tools/render_map.py <id> --scale 4 --grid --annotate` re-renders one map
larger, with a coordinate grid and spawn/portal/NPC/sign markers.

**Rule: never change a painter without regenerating and looking at the result.**
Art you did not look at is not finished. These renders need no Godot and no
browser — they read `terrain.png` and the map JSON directly and take about a
second.

**Working on lighting?** None of the sheets above can help you: they read
`terrain.png` and the map JSON directly, so an ambient modulate, a light
falloff and a baked occluder are all invisible to them. Those exist only once
Godot is drawing, so there is a second loop for them:

```bash
tools/ci.sh shots      # boots the real game on a virtual display (needs xvfb)
```

then look at `docs/shots/*.png` — the game as a player sees it, at the places
`tools/shoot.gd` lists. Add a row there when you add a lighting behaviour a
still frame can prove. These are reference images, not build outputs: they
come out of whatever GL driver the machine has, so they live outside the
drift-checked `docs/art/` and are regenerated on demand.

The sheets are committed, so GitHub shows a before/after image diff on any pull
request touching art. That is deliberate. Do not gitignore them.

## How the art is built

Every shipped pixel is drawn by code and byte-reproducible. CI regenerates
everything and fails if the committed result differs.

```
tools/pixel.py    Canvas, PNG read/write, the palette P, a 3×5 font, and the
                  isometric primitives: diamond_span, fill_diamond, prism, blob.
tools/gen_art.py  every t_<tile> painter, the e_<tile> emission painters, the
                  ACTORS table, the light falloff. Draws the real art.
assets/tiles/tiles.json      the tile registry: name -> atlas cell + solid flag
                             + optional "lighting" metadata (emit/occluder/emission)
assets/tiles/terrain.png     GENERATED. Never hand-edit.
assets/tiles/terrain_emission.png  GENERATED. Self-lit pixels, same layout.
assets/tiles/terrain.tres    GENERATED by tools/build_tileset.gd. Never hand-edit.
assets/lights/point_light.png      GENERATED. The banded PointLight2D falloff.
assets/sprites/actors.png    GENERATED. Never hand-edit.
docs/art/*.png               GENERATED. Never hand-edit.
```

### The cell a painter fills

```
row 0   +----------------+  headroom, 24px. Walls, roofs, canopies grow up
        |                |  into this. Nothing may be taller than the headroom
row 23  |                |  or it is clipped out of its own cell.
row 24  |      /\        |  the ground diamond, 32x16. The tile's footprint,
        |    /    \      |  and the only part that meets its neighbours.
row 39  |      \/        |
row 40  |                |  padding. Never draw here. It exists to centre the
row 63  +----------------+  footprint, which is why terrain.tres needs no offset.
```

You should not be counting rows. Build ground with `ground()`, solids with
`block()` or `small_block()`, stand props on `foot_shadow()`, and draw lines
along the grid with `axis_line()` — they all take footprint coordinates.

Two rules the isometric grid adds:

- **Nothing may touch the diamond's edge unless it is meant to continue into
  the next tile.** A highlight that reaches an edge meets the identical
  highlight on the neighbour and rules the whole field into a lattice. That is
  what `t_water` keeps its crests short for.
- **Transitions run along a grid edge, not across the middle.** A coastline in
  the maps runs along a row, which on screen is the cells' north-east edge —
  `_north_band()` is what draws it. Splitting the diamond horizontally instead
  draws a straight line through a world that has no straight lines.

**To add a tile:** add it to `tiles.json` with a free atlas cell and the right
`solid` flag → add a `t_<name>` painter in `gen_art.py` and register it in
`PAINTERS` → `tools/ci.sh generate` → look at `docs/art/atlas.png` →
`tools/ci.sh test`. Never write an atlas coordinate anywhere except
`tiles.json`. If the tile should glow, block light or stay lit in the dark,
that is a `"lighting"` block on the same entry (plus an `e_<name>` painter for
`"emission"`) — `docs/architecture/AGENTS.md` has the checklist.

**To add a character:** add a row to `ACTORS` in `gen_art.py` (name plus four
hex colours) → `tools/ci.sh generate` → look at `docs/art/actors.png`.

**To use art you did not draw:** put the sheet in `assets/packs/<name>/` with a
`pack.json`, then give the tile a `"pack"` in `tiles.json` instead of writing a
painter. `assets/packs/README.md` has the format and the two ways a downloaded
sheet usually fails to fit. This does not weaken the CI drift check — the sheet
is a source and `terrain.png` is still rebuilt from it every time.

Painters use `noise()` for texture so output stays deterministic across runs;
never use `random`. Colours come from `P` in `tools/pixel.py` — if you need a
new one, add it there rather than inlining a hex value.

## The one rule all art obeys

**A sprite may rise as far above its cell as it likes, and may never sink below
the ground diamond it stands on.**

That is the whole contract, and `tools/ci.sh art` enforces it on every tile,
drawn or imported. It is what lets a tree overhang its neighbours while its
trunk still meets the floor at a known place — and sorting the world by ground
contact is only correct because it holds. A sheet drawn on somebody else's grid
will break it, silently, in a way that looks fine on a contact sheet and wrong
the moment forty tiles sit together.

## What the art actually needs

Open `docs/art/map_port_azure_town.png` and the problems are visible at a
glance. In rough order of payoff:

**1. Terrain transitions.** `shore` and `dune_edge` band along a cell's
north-east edge, which is right for a coastline running along a grid row and
wrong for every other direction — a bay, an inlet or a river would need edge
variants. Godot 4 has terrain sets built in, and using them means **the ASCII
map format does not have to change**: `tiles.json` grows terrain metadata,
`tools/build_tileset.gd` builds the terrain set and peering bits, and
`scripts/map_loader.gd` `_paint()` switches to `set_cells_terrain_connect()`
per terrain group so Godot picks the variant. On a diamond grid the four
peering bits that matter are the cell's four *edges*, not its corners, so a
16-tile edge set per pair covers it. Non-terrain tiles (furniture, walls,
props) keep the direct `set_cell()` path.

**2. Ambient occlusion.** Props drop a `foot_shadow()` and actors carry their
own, but nothing darkens where a wall meets the floor, and a block casts no
shadow onto the cell beside it. Both are pure painter work and both would do a
lot to seat the blocks into the ground.

**3. Animation.** Water, the fireplace and lamps are static.
`TileSetAtlasSource` animates by consuming **horizontally adjacent** atlas
cells, which the current 8-column layout has no room for — water at `(4,0)`
would eat `(5,0)` and `(6,0)`, which are `sand` and `tree`. So the atlas has to
be re-laid-out first, giving animated tiles their own rows with frame space
reserved. Add a `frames: N` field to `tiles.json`, draw each frame, and call
`set_tile_animation_frames_count()` / `set_tile_animation_frame_duration()` in
the baker. `TileRegistry.atlas_columns` and the atlas bounds assertion in
`tests/test_data.gd` follow.

**4. Repetition.** The tree border down both edges of the town is one tile
stamped forty times, and it is more obvious now that a tree is a tall rounded
mass rather than a flat square. Variant tiles chosen by position would break it
up.

**5. Height.** Every tile stands on the same ground plane; a roof is just a
taller block than the wall in front of it. Real elevation — a `height` field
per cell, a dock above the water, a cliff — is the thing an isometric world
buys you that a top-down one cannot, and nothing in the current data model
uses it.

Verify the exact Godot 4.7.2 API names against the local binary before writing
the baker changes — `set_terrain_peering_bit` and `set_cells_terrain_connect`
are the two worth checking.

## Reference art from an image model

Optional, and never shipped:

```bash
export OPENAI_API_KEY=...
python3 tools/gen_art_ai.py "grass-to-shoreline transition, isometric 2:1 diamond tiles"
# -> docs/art/refs/<slug>.png  (gitignored)
```

Look at the result, then write the painter that matches it in this project's
palette. The model is for composition and colour ideas; the pixels stay
code-generated. `gpt-image-2` is the default and does not support transparent
backgrounds — use `--model gpt-image-1.5 --transparent` when you need alpha.

## Rules that keep the loop working

- **Never hand-edit a generated file.** `terrain.png`, `terrain.tres`,
  `actors.png`, `actors.json`, everything in `docs/art/`. CI regenerates them
  and fails on any difference.
- **Never put map content in a `.tscn`.** A `TileMapLayer` stores cells as a
  binary blob you cannot read, review or diff. Maps are ASCII grids in
  `maps/*.json`; `scripts/map_loader.gd` builds the layers at runtime.
- **Keep every map layer rectangular.** A short row silently becomes empty
  space and usually opens a hole in a wall.
- **A change is not done until `tools/ci.sh test` passes**, and art changes are
  not done until you have looked at the render.

## What the tests already check

Do not re-implement these — 64 tests cover: every script parses and every scene
instantiates; the baked tileset matches `tiles.json` tile-for-tile and
solid-for-solid and is still an isometric diamond grid; `scripts/iso.gd`
projects cells exactly where a real `TileMapLayer` does, both ways; every map
is rectangular with a complete legend; **a flood fill
from each spawn reaches every door, NPC and sign** (this is what catches a
staircase sealed behind a table); doors lead both ways; every dialogue node is
reachable and can reach an ending; and the game boots headlessly, walks the
player into walls, steps through every door and interacts with everything.
Lighting is pinned too: profiles and tile lighting metadata validate, baked
occluders and emission pixels match `tiles.json`, emitting tiles spawn real
`PointLight2D`s that are swept on map change, a map with no `"lighting"` block
renders full-bright, and the renderer/viewport settings the pixel look and the
web build depend on are asserted verbatim.

When you add a mechanic, add the test that would fail without it. See
`tests/test_runtime.gd::test_facing_an_interactable_finds_it` for the shape of a
good one — it exercises the path a player actually takes, not the function you
just wrote.

## Code style

GDScript: static typing everywhere (`var x: int`, `-> void`), `snake_case`
members, `PascalCase` for `class_name`, past-tense signals (`map_changed`).
Python: standard library, 4-space indent, module docstring saying what the
script writes. Comment the *why*; the *what* is in the code. Match the
surrounding file.
